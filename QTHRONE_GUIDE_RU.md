# qThrone: загрузка, сборка и обновление

Это исходники форка Throne с профилями qWDTT (RAW/WG). Готовый GUI-релиз получается через GitHub Actions. Архив исходников сам по себе не является установленным приложением.

## Что добавлено

- Протокол `qWDTT (RAW)` / `qWDTT (WG)` в таблице профилей.
- RAW по умолчанию при создании и импорте без явно указанного режима. Явное `mode=wg` сохраняется.
- Редактор в стиле Throne: четыре отдельных поля хешей, пароль, RAW-порт, воркеры, UDP/TCP для TURN, Audio/Video, DNS для VK и ID устройства. Адрес сервера и основной порт — общие поля Throne.
- Ссылки `qwdtt://config?...`, `qwdtt:config?...`, старые `wdtt://...`, текстовые/Base64-подписки и JSON-профили, массивы, обёртки `profiles`/`servers`.
- Системный прокси и TUN через штатное ядро Throne. Локальный qWDTT SOCKS5 поддерживает TCP и UDP и требует случайный пароль. Порты выделяются автоматически.
- Белая иконка при включённом TUN: исходный контур, прозрачность и сглаживание сохранены.
- Имя приложения qThrone, архивы релиза qThrone, отдельные каталоги установки и имя Linux-пакета `qthrone`.
- Проверка обновлений берёт ваш `owner/repository` из окружения GitHub Actions при сборке. Обновления оригинального Throne напрямую в форк не устанавливаются.

Исполняемый GUI-файл внутри релиза по-прежнему называется `Throne.exe` / `Throne`, а приложение macOS — `Throne.app`: это сохраняет штатные скрипты, механизм привилегий и updater. В интерфейсе имя qThrone.

## 1. Загрузить на GitHub без установки программ на ПК

Рекомендуется настоящий Fork, чтобы сохранить связь с upstream. Для загрузки используйте браузерный GitHub Codespaces. Сборка после этого идёт в Actions; локальные Go, Qt, Visual Studio и WireGuard не нужны.

1. Откройте https://github.com/throneproj/Throne и нажмите **Fork**. Назовите репозиторий `qThrone`. Если доступен выбор ветки, используйте `dev`.
2. В своём форке выберите **Code → Codespaces → Create codespace**. Дождитесь браузерного редактора. Codespaces и Actions имеют отдельные квоты вашего аккаунта; наличие доступной квоты нужно проверить в GitHub.
3. В распакованном комплекте найдите файл `qThrone.bundle`. Перетащите его в корень дерева файлов браузерного Codespaces. Он нужен только для импорта подготовленного коммита; не добавляйте его в Git.
4. Откройте терминал Codespaces и выполните:

```bash
git fetch https://github.com/throneproj/Throne.git 32138a44967ef24dcf5bf99645617933c9b9f9ec
git bundle verify ./qThrone.bundle
git fetch ./qThrone.bundle qthrone
git switch -c qthrone FETCH_HEAD
git push -u origin qthrone
```

`qThrone.bundle` — компактный Git bundle с изменениями относительно указанного коммита Throne. Первый fetch загружает необходимую базу. Это сохраняет настоящую историю проекта и права исполнения скриптов.

После успешного `git push` удалите загруженный `qThrone.bundle` из дерева файлов Codespaces. Он уже не нужен там и иначе будет считаться незакоммиченным файлом при будущем запуске скрипта обновления. Оригинал bundle остаётся в вашем скачанном комплекте.

5. В настройках репозитория сделайте **qthrone** веткой по умолчанию. Путь в интерфейсе GitHub: **Settings → Default branch** (иногда находится в General или Branches).
6. В **Actions** разрешите workflows для форка. После работы остановите Codespace через меню Codespaces.

Если `git push` отклонён политикой организации или ограничениями токена на `.github/workflows`, используйте личный репозиторий либо выданные владельцем права на изменение workflows. Не удаляйте workflows ради обхода ошибки: без них релиз не соберётся.

Папка `qThrone-src` в комплекте содержит полные исходники и пригодна для обычного Git-клиента. Однако загрузка всех файлов через **Add file → Upload files** может упереться в лимит числа файлов и потерять executable-биты shell-скриптов. Поэтому для варианта «только браузер» предпочтителен bundle + Codespaces.

## 2. Собрать первый релиз в GitHub Actions

1. Откройте **Actions → qWDTT tests**, при необходимости нажмите **Run workflow**, выберите ветку `qthrone`. Дождитесь зелёных проверок Linux, Windows и macOS.
2. Откройте **Actions → qThrone release → Run workflow**.
3. Выберите `qthrone`. В `tag` введите, например, **1.0.0**. Используйте числовой вариант без `v`: он подходит и для Debian-пакетов.
4. В `publish`:
   - `p` — опубликовать предварительный релиз; рекомендуется для первой сборки;
   - `r` — обычный стабильный релиз;
   - пусто — только собрать и получить артефакты Actions, без GitHub Release.
5. Дождитесь окончания workflow. Он проверяет qWDTT, собирает Go-ядра, GUI на Qt и упаковывает Windows, Linux и macOS. Матрица и зависимости сохранены из оригинального Throne. Это не мгновенная сборка: длительность зависит от очереди runners, скачивания Qt/Chromium и попадания в кэш; ориентируйтесь на десятки минут, первая сборка может занять больше часа.
6. При `p` или `r` файлы появятся в **Releases** вашего репозитория. При пустом `publish` скачайте артефакт **Deployment-...** со страницы завершённого запуска.

Для обычного Windows x64 нужен архив **qThrone-1.0.0-windows64.zip** или **windows-universal-installer.exe**. В ZIP запускайте `Throne/Throne.exe`. Рядом должны находиться `ThroneCore.exe` и `qwdtt.exe`; не переносите один GUI-файл отдельно. Для TUN нужны права, которые обычно требует Throne. Системный прокси подключается штатным переключателем Throne.

Workflow оригинала для AUR и публикации APT/RPM-репозиториев выключен в форках: он требует секреты команды Throne. Сборка и публикация обычных GitHub Releases доступны вашему форку без этих секретов. Неподписанный установщик может показывать стандартное предупреждение Windows об издателе; сертификат подписи в этот комплект не входит.

Если workflow упал, откройте красный job и первый завершившийся ошибкой шаг. Установка компиляторов на вашем ПК это не исправит: сборка выполняется на runner GitHub. Полный GUI-релиз в рамках подготовки этого архива ещё не запускался в вашем GitHub-репозитории, поэтому первый Actions-запуск обязателен.

## 3. Настроить qWDTT

Создайте профиль qWDTT или импортируйте ссылку/подписку обычным способом Throne. Затем откройте редактор.

| Поле | Значение |
|---|---|
| Адрес сервера | IP или домен VPS, без схемы `http://` |
| Основной порт сервера | DTLS-порт для WG, обычно `56000`; это не внутренний порт WireGuard `56001` |
| Режим | RAW по умолчанию, WG для WireGuard внутри qWDTT |
| Порт RAW на сервере | Обычно `56003`; должен совпадать с отдельным RAW listener сервера |
| Пароль | Пароль подключения qWDTT/PWDTT, согласованный с сервером |
| Хеш VK 1–4 | От одного до четырёх хешей; можно вставлять ссылки на звонок VK |
| Воркеры | Общее число потоков ядра, кратное 9, от 9 до 108; по умолчанию 9 |
| Транспорт TURN | UDP по умолчанию; TCP при необходимости |
| Маскировка | Audio по умолчанию; Video при необходимости |
| DNS для VK | `yandex` по умолчанию; поддерживаются исходные варианты ядра, включая `custom:IP` и `doh:URL` |
| ID устройства | Создаётся автоматически и сохраняется; для привязанного пароля нужен ID, разрешённый вашим сервером |

Пример ссылки с фиктивными значениями:

```text
qwdtt://config?name=Example&peer=203.0.113.10%3A56000&pass=CHANGE_ME&hashes=HASH1,HASH2&raw_port=56003
```

Без `mode` импортируется RAW. Для WG добавьте `&mode=wg`. Пароль, имя, хеши и прочие значения со специальными символами должны быть URL-кодированы. Экспорт из редактора делает это автоматически. Экспортируемая ссылка содержит пароль и хеши, поэтому обращайтесь с ней как с настройками доступа.

RAW требует сервер qWDTT с поддержкой RAW и включённым RAW listener. На старом сервере PWDTT, который умеет только WG, выберите WG. Нельзя получить RAW одной заменой клиентского интерфейса на сервере без RAW-поддержки. Сервер автоматически не устанавливается и его конфигурация этим архивом не меняется.

После запуска дождитесь сообщения `[qWDTT] SOCKS bridge ready` в журнале. Получение TURN-доступа и конфигурации сервера происходит до открытия внутреннего SOCKS-входа; сразу после нажатия «Запустить» доступ ещё может отсутствовать.

Для системного прокси включите штатный переключатель **Системный прокси**. Для всего поддерживаемого системного трафика включите **TUN**. Как и в обычном Throne, режим системного прокси действует на приложения, которые учитывают системные настройки прокси; произвольный системный UDP требует TUN или явного SOCKS5 UDP клиента.

## 4. Что проверено и что ещё нужно проверить

Восемь локальных Go-тестов проходят: пароль SOCKS5, TCP/UDP, IPv4/IPv6/domain-кодирование адреса SOCKS, TCP half-close, RAW-конфигурация, RAW-передача между двумя виртуальными IP-стеками, передача TCP/UDP между двумя настоящими userspace WG-устройствами и приватный конфиг. `go vet` проходит. Кросс-сборки ядра проверены для Windows amd64/arm64/386, Linux amd64/arm64 и macOS amd64/arm64.

Отдельно скомпилированы C++-объекты профиля, редактора, фабрики профилей, импорта подписок и иконки с Qt 6.11.2. Это не полная сборка/линковка GUI и не визуальная проверка запущенного интерфейса. Полная сборка делается первым Actions-запуском. Проверка `-race` включена в CI; локальный race-runtime с доступным вспомогательным компилятором запустить не удалось.

Живое соединение VK → TURN → VPS, системный прокси/TUN на этом соединении и автообновление установленного GUI не проверены: при подготовке не было рабочего VPS, пароля и VK-хешей. Перед объявлением стабильного релиза проверьте оба режима на своём сервере, открытие сайтов через системный прокси, TCP/UDP через TUN, отключение/повторный запуск и восстановление штатных сетевых настроек при выходе. Архив не следует считать подтверждённым стабильным бинарным релизом до этих проверок.

Сохраняются ограничения штатных extra-core профилей Throne: qWDTT не включается в Auto Selector, массовые serverless-тесты и IP-сканер; в цепочке допускается только один extra-core в предусмотренном оригиналом крайнем положении. Обычный одиночный профиль предусмотрен для системного прокси и TUN. Нативный серверный протокол и IP-туннель используют IPv4, как исходный desktop SOCKS-клиент; поддержка IPv6-адреса в синтаксисе SOCKS не означает IPv6-доступ через VPS.

Для VK используется оригинальная анонимная авторизация и автоматическое решение капчи Go/RJS. Android WebView fallback не переносился в Qt: при неуспешном автоматическом решении появится ошибка в журнале, а не ожидание ответа отсутствующего Android-приложения. Вход через аккаунт VK и отдельный браузер капчи в интерфейс не добавлялись.

## 5. Обновлять Throne в будущем

Исходная база: `throneproj/Throne`, ветка `dev`, коммит `32138a44967ef24dcf5bf99645617933c9b9f9ec`.

Откройте Codespaces на ветке `qthrone`, убедитесь, что локальных незакоммиченных изменений нет, и выполните:

```bash
bash script/sync_upstream.sh
```

Скрипт получает актуальную `dev` оригинала и создаёт отдельную ветку `qthrone/upstream-<дата-время>`, затем выполняет merge. В случае конфликтов исправляйте их именно в этой ветке; отмена незавершённого merge — `git merge --abort`. Результат не публикуется автоматически.

После успешного merge:

```bash
git push -u origin HEAD
```

Создайте Pull Request в `qthrone`. Запустите **qWDTT tests** и **qThrone release** для этой ветки с пустым `publish` или предварительным релизом, проверьте бинарники и только затем объединяйте PR. Следующий стабильный релиз выпускайте с увеличенным номером, например `1.0.1`.

Код qWDTT отделён в папке `qwdtt`, профиль/редактор — в собственных файлах. Основные точки конфликтов с Throne: фабрика протоколов, редактор, SubscriptionParser, `generate.cpp`, иконка и сборочные скрипты. Поэтому «Sync fork» без разбора конфликтов не гарантирует сохранение интеграции.

Обновление самого qWDTT делается отдельно: сравнить новые `go_client` исходного Android-проекта с `qwdtt/`, сохранить desktop-адаптацию и мост, выполнить тесты и проверить серверную совместимость. Не заменяйте всю папку вслепую: потеряются RAW netstack, SOCKS UDP и приватный конфиг.
